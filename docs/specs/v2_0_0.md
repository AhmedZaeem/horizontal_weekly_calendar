## Context

Version 2.0 turns `horizontal_weekly_calendar` into an adaptive Flutter calendar UI kit while keeping its original promise: adding a polished, highly customizable horizontal calendar must stay easy. The release is a ground-up implementation with a compatibility layer for 1.x consumers.

The package must solve the failure modes reported against 1.x: missing or duplicated dates, incorrect direction callbacks, event placement that does not match the visible day, fixed-size `RenderFlex` overflows, incomplete cross-year navigation, and APIs that appear configurable but do nothing.

### Product principles

1. **Easy first.** A useful horizontal calendar requires a date and one selection callback; advanced behavior is opt-in.
2. **Correct by construction.** Calendar days use civil-date arithmetic and canonical date-only values, never elapsed-duration arithmetic.
3. **Adaptive, not merely recolored.** Material, Cupertino, and neutral styles have appropriate shape, motion, typography, controls, and hit targets.
4. **Composable.** Builders and theme tokens can replace presentation without forking navigation, selection, or date logic.
5. **Migration-safe.** Existing 1.x source continues to compile through deprecated public wrappers.
6. **Accessible and resilient.** RTL, large text, keyboard use, narrow screens, dark mode, high contrast, and reduced motion are first-class inputs.

## Functional Requirements

### Core API and compatibility

- FR-1: The package MUST expose its 2.0 API from `package:horizontal_weekly_calendar/horizontal_weekly_calendar.dart`.
- FR-2: `package:horizontal_weekly_calendar/weekly_calendar.dart` MUST remain importable and MUST export every public 1.3.0 symbol.
- FR-3: Every 1.3.0 widget, constructor, enum, typedef, and public utility retained for compatibility MUST carry `@Deprecated` documentation that names the 2.0 replacement.
- **FR-4:** A compatibility test application using the documented 1.3.0 examples MUST compile without source changes other than accepting deprecation warnings.
- **FR-5:** Public 2.0 libraries MUST NOT import the legacy barrel file or create circular imports.
- **FR-6:** Configuration properties in the 2.0 public API MUST either affect documented behavior and have a test, or MUST NOT be public.

### Date, navigation, and selection behavior

- **FR-7:** The horizontal calendar MUST render a contiguous ordered sequence of unique civil dates for the requested visible interval.
- **FR-8:** Date identity MUST compare year, month, and day only; time-of-day MUST NOT change selection, event bucketing, or disabled-state identity.
- **FR-9:** Navigation MUST work across week, month, year, leap-year, and daylight-saving boundaries without skipping or duplicating a date.
- **FR-10:** Consumers MUST be able to constrain navigation and selection with inclusive `minimumDate`, inclusive `maximumDate`, and a `selectableDayPredicate`.
- **FR-11:** The 2.0 API MUST support controlled single-date selection, multiple-date selection, and contiguous date-range selection.
- **FR-12:** A lightweight controller MUST expose focused-date navigation, previous/next page, today, selection updates, and fold state without requiring `GlobalKey` access.
- **FR-13:** Selection callbacks MUST report the previous and next values exactly once per accepted user action.
- **FR-14:** Navigation callbacks MUST report the actual chronological direction and focused interval after state resolution.
- **FR-15:** The horizontal calendar MUST support configurable visible-day count and first-day-of-week while preserving contiguous unique dates.

### Flagship horizontal calendar

- **FR-16:** `HorizontalCalendar` MUST provide a useful default presentation with no mandatory styling configuration.
- **FR-17:** The default horizontal calendar MUST support tap selection, horizontal swipe/page navigation, programmatic navigation, today indication, disabled dates, and event indicators.
- **FR-18:** Consumers MUST be able to customize day cells, headers, navigation controls, event indicators, selection decoration, spacing, padding, typography, shape, color, elevation, and motion through typed theme data and focused builders.
- **FR-19:** Builder contexts MUST include the normalized date and explicit states for today, selected, focused, disabled, outside interval, and event count.
- **FR-20:** Compact layouts MUST degrade deliberately by changing label density or scrolling; they MUST NOT rely on clipped `Row` children.

### Adaptive design system

- **FR-21:** Every 2.0 calendar widget MUST support `CalendarStyle.adaptive`, `material`, `cupertino`, `neutral`, and a fully custom theme.
- **FR-22:** Adaptive style MUST resolve to Cupertino conventions on Apple platforms and Material conventions on Android/Fuchsia unless overridden.
- **FR-23:** `HorizontalCalendarThemeData` MUST be a Flutter `ThemeExtension` and MUST support `copyWith` and `lerp`.
- **FR-24:** Material and Cupertino presets MUST use platform-appropriate navigation controls, feedback, corner treatment, motion curves, and minimum interactive target sizes.
- **FR-25:** The package MUST provide light, dark, and high-contrast token values without requiring a consumer to copy internal source.
- **FR-26:** All motion MUST honor `MediaQuery.disableAnimations`; consumers MUST be able to set duration and curve tokens.

### Foldable week-to-month calendar

- **FR-27:** `FoldableCalendar` MUST display one focused week in the collapsed state and a complete month grid in the expanded state.
- **FR-28:** Expanding or collapsing MUST preserve the selected date and MUST keep the focused date visible.
- **FR-29:** Fold state MUST be controllable by header action, vertical drag when enabled, and `HorizontalCalendarController`.
- **FR-30:** Month rows MUST expand to the exact number needed by the displayed month and configured first day of week; outside-month dates MUST follow a configurable visibility policy.
- **FR-31:** A fold action during an in-flight fold animation MUST converge on the latest requested state without throwing or leaving an intermediate height.
- **FR-32:** Collapsed and expanded layouts MUST share the same selection, disabled-date, locale, event-indicator, and theme semantics.

### Calendar UI kit widgets

- **FR-33:** The 2.0 release MUST include a reusable month grid powered by the same date and selection model as the horizontal calendar.
- **FR-34:** The 2.0 release MUST include an agenda list that groups events by civil date and supports empty/loading/error states.
- **FR-35:** The 2.0 release MUST include day and week timeline views with configurable hour range, interval height, all-day area, current-time indicator, and overlap layout.
- **FR-36:** UI-kit widgets MUST be independently usable and MUST NOT require the flagship horizontal strip as an ancestor.
- **FR-37:** Common headers, date pills, event tiles, all-day rows, and now indicators MUST be available as public composable widgets or builders where doing so avoids duplicated consumer UI.

### Events

- **FR-38:** `CalendarEvent<T>` MUST represent an identifier, start, end, optional title, optional metadata, optional color, and all-day state.
- **FR-39:** Events with `end <= start` MUST be rejected in debug builds and documented as invalid input.
- **FR-40:** Timed, all-day, multi-day, and cross-midnight events MUST be assigned to every intersected visible civil date without duplicate identity on a date.
- **FR-41:** Overlapping timed events MUST receive deterministic non-overlapping horizontal columns; chained overlaps MUST remain in one collision group.
- **FR-42:** Consumers MUST be able to provide events synchronously or through an async `CalendarEventSource` queried by visible interval.
- **FR-43:** Async event requests MUST expose loading and error states, MUST ignore stale out-of-order results, and MUST not request the same unchanged interval repeatedly.
- **FR-44:** Event tap and long-press callbacks MUST return the original typed `CalendarEvent<T>`.

### Localization, directionality, and accessibility

- **FR-45:** Calendar labels MUST use the ambient locale by default and support an explicit locale override.
- **FR-46:** Weekday labels MUST be formatted using locale-aware patterns or consumer-provided formatters; implementation MUST NOT truncate localized strings by UTF-16 substring.
- **FR-47:** RTL MUST reverse visual navigation and gesture expectations while chronological previous/next controller methods retain their semantic meaning.
- **FR-48:** Every interactive date MUST expose a semantics label containing its full localized date and selected/today/disabled/event-count state as applicable.
- **FR-49:** Keyboard users MUST be able to move focus by day and week, activate selection, move to today, and traverse interactive controls in chronological order.
- **FR-50:** Default interactive targets MUST be at least 48 logical pixels for Material and 44 logical pixels for Cupertino.
- **FR-51:** At text scale factors up to 2.0, essential date information MUST remain available through wrapping, adaptive density, or semantic labels without layout exceptions.

### Example, documentation, and package quality

- **FR-52:** `example/` MUST be a standalone Flutter application runnable on Android, iOS, and web.
- **FR-53:** The example MUST provide a discoverable gallery for adaptive, Material, Cupertino, neutral, foldable, event timeline, agenda, RTL, large-text, dark-mode, and custom-builder scenarios.
- **FR-54:** The README MUST lead with a minimal horizontal-calendar example, then cover customization, adaptive styling, events, accessibility, and the UI-kit widgets.
- **FR-55:** A migration guide MUST map each 1.3.0 widget and parameter to its 2.0 replacement and call out any behavior correction.
- **FR-56:** Public API documentation MUST include runnable examples for the flagship calendar, controller, foldable calendar, theme, events, agenda, and timeline.
- **FR-57:** CI MUST run formatting verification, static analysis, unit/widget/golden tests, example analysis, package dry-run, and package scoring checks.

## Non-Functional Requirements

- **NFR-COR-1:** Property-based date-generation tests MUST cover every month from 1900-01 through 2100-12, every configured week start, leap days, and DST transition fixtures; each result MUST be strictly increasing by one civil day with no duplicates.
- **NFR-COR-2:** Selection and event bucketing tests MUST cover non-midnight inputs and at least `UTC`, a spring-forward zone, a fall-back zone, and a zone with a non-whole-hour offset where the test runtime supports them.
- **NFR-REL-1:** Widget stress tests MUST complete 500 randomized combinations of bounds, focused date, selection mode, first weekday, visible-day count, locale direction, width, and text scale with zero uncaught framework exceptions.
- **NFR-LAY-1:** Golden/widget matrices at widths 280, 320, 375, 430, 768, and 1440 logical pixels and text scales 1.0, 1.3, 1.6, and 2.0 MUST produce zero overflow or `RenderFlex` exceptions.
- **NFR-PERF-1:** In profile benchmark tests on the repository's reference simulator/device, changing a simple seven-day page MUST have a p95 frame build time below 16 ms after warm-up.
- **NFR-PERF-2:** Laying out 1,000 events in a seven-day timeline fixture MUST complete in under 100 ms on the repository's reference development machine, recorded with the benchmark environment.
- **NFR-ACC-1:** Automated semantics tests MUST verify labels, selected/today/disabled flags, chronological traversal, and keyboard actions for the flagship and foldable calendars.
- **NFR-ACC-2:** Default foreground/background pairs MUST meet WCAG 2.2 AA contrast: 4.5:1 for normal text and 3:1 for large text and essential non-text indicators.
- **NFR-API-1:** The public API MUST contain no exported `src/` implementation types unless intentionally documented as public.
- **NFR-COMP-1:** A fixture pinned to the 1.3.0 documented API MUST compile against 2.0 with deprecation warnings and no errors.
- **NFR-QA-1:** `dart format --output=none --set-exit-if-changed .`, `flutter analyze`, all tests, and example analysis MUST exit successfully.
- **NFR-QA-2:** `dart pub publish --dry-run` MUST report no warnings attributable to the package.
- **NFR-QA-3:** The release candidate MUST achieve the maximum attainable pub.dev package score, targeting 160/160 under the current `pana` version, with any external scoring limitation documented.
- **NFR-MAINT-1:** New production files MUST keep calendar arithmetic, controller/state, theme, event layout, and widgets in separate layers with no dependency cycle.
- **NFR-DEP-1:** Runtime dependencies MUST be minimal; each non-SDK dependency MUST have a documented reason and a maintained, null-safe version range.

## Acceptance Criteria

### AC-1: Unique civil-date generation (FR-7, FR-9; NFR-COR-1)

Given a generated interval crossing any tested month, year, leap day, or DST boundary, when dates are enumerated, then each civil date appears exactly once in chronological order.

### AC-2: Legacy source compatibility (FR-1, FR-2, FR-3, FR-4, FR-5, FR-6; NFR-COMP-1)

Given the 1.3.0 compatibility fixture, when it is analyzed and compiled against 2.0, then it succeeds and reports only expected deprecation diagnostics.

### AC-3: Controlled navigation and selection (FR-8, FR-10, FR-11, FR-12, FR-13, FR-14, FR-15)

Given controlled bounds and selection, when a user navigates or selects, then only valid actions change state and callbacks contain the exact previous/next values and actual direction once.

### AC-4: Resilient flagship layout (FR-16, FR-17, FR-18, FR-19, FR-20; NFR-LAY-1)

Given every required width and text-scale combination, when the horizontal calendar is pumped and interacted with, then it remains usable with zero framework overflow exceptions.

### AC-5: Adaptive design system (FR-21, FR-22, FR-23, FR-24, FR-25, FR-26)

Given each style mode and brightness/contrast/motion setting, when the calendar resolves its theme, then the documented platform preset, target size, tokens, and motion behavior are applied.

### AC-6: Foldable behavior (FR-27, FR-28, FR-29, FR-30, FR-31, FR-32)

Given a selected date in a collapsed week, when the calendar expands, changes month, and collapses, then selection is preserved, the focused date remains visible, and the final height matches the latest requested fold state.

### AC-7: UI-kit composition (FR-33, FR-34, FR-35, FR-36, FR-37)

Given a consumer uses a month grid, agenda, or timeline independently, when the widget is rendered without a horizontal-calendar ancestor, then it shares the documented date/theme model and exposes its composable parts.

### AC-8: Event segmentation and layout (FR-38, FR-39, FR-40, FR-41, FR-42, FR-44)

Given overlapping, multi-day, all-day, and cross-midnight events, when the visible interval is laid out, then every intersected date has one correct segment and timed segments never overlap horizontally within a collision group.

### AC-9: Async event ordering (FR-43)

Given two async interval requests that finish in reverse order, when both complete, then only the newest interval result is displayed and unchanged intervals are not re-requested.

### AC-10: Localization and accessibility (FR-45, FR-46, FR-47, FR-48, FR-49, FR-50, FR-51; NFR-ACC-1)

Given RTL, a localized locale, keyboard input, and text scale 2.0, when the user navigates and selects, then visual direction is correct, full labels remain meaningful, focus order is chronological, and semantics report all relevant states.

### AC-11: Runnable documentation and gallery (FR-52, FR-53, FR-54, FR-55, FR-56)

Given a new package consumer, when they run the example and follow the README, then they can launch every gallery scenario and reproduce the documented minimal, adaptive, foldable, agenda, and timeline examples.

### AC-12: Release quality gate (FR-57; NFR-QA-1, NFR-QA-2, NFR-QA-3)

Given the release candidate, when the full quality gate runs, then formatting, analysis, tests, dry-run publish, and package scoring all pass at the documented target.

## Edge Cases

- EC-1: `minimumDate` and `maximumDate` fall on the same civil day.
- EC-2: `minimumDate` is after `maximumDate`; constructors assert with an actionable message.
- EC-3: Controlled selected or focused dates are outside bounds; focus clamps and invalid selections are ignored without callback loops.
- **EC-4:** A consumer does not rebuild with a callback's proposed controlled value; the widget continues to reflect the supplied value.
- **EC-5:** February 29 in leap years, February 28 in non-leap century years, and the year 2000.
- **EC-6:** Local midnight near spring-forward, fall-back, historical offset changes, and non-whole-hour offsets.
- **EC-7:** Week and month intervals crossing December/January and minimum/maximum years supported by Dart `DateTime`.
- **EC-8:** Visible-day counts of 1 and a documented upper bound, plus a viewport narrower than the preferred day-cell width.
- **EC-9:** Empty, one-grapheme, and long localized weekday/month labels.
- **EC-10:** RTL gestures, keyboard arrows, page controls, and semantic previous/next labels.
- **EC-11:** Text scale 2.0 with bold text, high contrast, and a 280-pixel viewport.
- **EC-12:** Parent removal, hot reload, controller replacement, and controller disposal during animation or async event loading.
- **EC-13:** Fold toggled repeatedly or reversed mid-animation and fold state updated externally during drag.
- **EC-14:** Month views needing four, five, or six rows; outside-month dates hidden, visible, or visible-disabled.
- **EC-15:** No events, thousands of events, same-start events, nested overlaps, chained overlaps, and identical IDs supplied accidentally.
- **EC-16:** Events starting before the visible range, ending after it, crossing midnight, spanning DST, or covering multiple full days.
- **EC-17:** Async event source throws, returns stale data, returns duplicates, or completes after widget disposal.
- **EC-18:** `MediaQuery.disableAnimations` becomes true during an animation.
- **EC-19:** Theme changes between Material, Cupertino, neutral, brightness, and contrast at runtime.
- **EC-20:** Nested horizontal scrollables and gesture arbitration between day-strip paging, timeline scrolling, and fold dragging.

Callback contracts:

| Callback | Contract |
| --- | --- |
| `onSelectionChanged` | Called once with a normalized proposed controlled selection after an accepted user action; never called for disabled or unchanged selection. |
| `onFocusedDateChanged` | Called once when the user or controller moves focus to a different normalized civil date. |
| `onFoldStateChanged` | Called once when a user action proposes a different controlled fold state. |
| `onEventTap` / `onEventLongPress` | Returns the original typed event, not an internal segment. |

## Data Models

| Model | Key fields | Invariants |
| --- | --- | --- |
| Civil date | year, month, day | Canonicalized to local date-only construction; equality ignores time-of-day. |
| Visible interval | start inclusive, end exclusive | `start < end`; day generation advances by civil constructor values. |
| Selection | mode plus date(s)/range | Dates canonical, multiple values unique, range ordered and inclusive. |
| Event | id, start, end, all-day, payload | `end > start`; source result is deduplicated by event ID before layout. |
| Event segment | source event, visible date, clipped start/end | One segment per event ID per intersected civil date. |
| Theme | semantic colors, type, shape, spacing, motion | Complete resolved theme has no null token required by rendering. |
| Fold state | collapsed/expanded plus animation progress | Stable state is exactly 0 or 1; latest command owns the target. |

Date arithmetic rule: advance a civil date with `DateTime(year, month, day + delta)` after canonicalization. Do not compute calendar days with `Duration(days: delta)` from an arbitrary zoned instant.

## Architecture boundaries

```text
public API / compatibility facade
              |
widgets ----- controller/state ----- themes
   |                |                  |
   +---------- calendar domain --------+
                      |
               event segmentation
                      |
                 event sources
```

- Domain date generation and event segmentation MUST NOT import Flutter widgets.
- Controllers MUST own intent and observable state, not render objects.
- Widgets MUST use resolved theme tokens and domain results rather than reimplementing date math.
- Compatibility wrappers MAY adapt legacy properties but MUST delegate to isolated legacy implementations or 2.0 primitives without leaking legacy types into new APIs.

## Test strategy

1. Write domain tests first for civil-date normalization, ranges, weeks, months, bounds, selection, event segmentation, and overlap groups.
2. Add controller tests for commands, controlled callbacks, latest-command behavior, and disposal.
3. Add widget tests for horizontal navigation, fold transitions, async event races, semantics, keyboard, RTL, and overflow matrices.
4. Add golden tests for adaptive/Material/Cupertino/neutral, light/dark/high-contrast, and representative phone/tablet sizes.
5. Keep a compile-only 1.3.0 compatibility fixture.
6. Run example integration smoke tests and profile benchmarks.
7. Finish with format, analyze, all tests, publish dry-run, and `pana`.

## Delivery phases

- **Phase A — foundation:** public entrypoint, domain model, controller, selection, theme system, deprecated compatibility facade.
- **Phase B — flagship:** production horizontal calendar, platform presets, builders, semantics, keyboard, RTL, overflow resilience.
- **Phase C — foldable and events:** foldable week/month, month grid, event model/source/indicators, agenda.
- **Phase D — timelines:** day/week timelines, all-day row, now indicator, deterministic overlap layout.
- **Phase E — gallery and release quality:** standalone example, Figma-aligned gallery, documentation, migration guide, goldens, benchmarks, CI, package score.

## Out of Scope

- OS-1: Parsing or generating iCalendar/ICS files.
- OS-2: A complete RFC 5545 recurrence-rule engine; consumers provide expanded instances in 2.0.0.
- **OS-3:** OS calendar account synchronization, remote persistence, authentication, reminders, or push notifications.
- **OS-4:** Resource/room scheduling, drag-to-resize, and drag-to-create event editing.
- **OS-5:** A built-in non-Gregorian chronology engine. The API may preserve room for future chronology adapters; 2.0.0 renders Gregorian `DateTime` civil dates.
- **OS-6:** Publishing, tagging, releasing, or pushing repository changes as part of implementation; those actions require separate explicit owner authorization.

## Definition of done

2.0.0 is ready for owner review only when AC-1 through AC-11 pass, the example gallery demonstrates the Figma-aligned designs on Android/iOS/web, the migration fixture compiles, the quality gates meet NFR-QA-1 through NFR-QA-3, and no repository content has been pushed, tagged, published, or released.
